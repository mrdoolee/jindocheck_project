# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install          # install dependencies
npm run dev           # start Vite dev server
npm test              # run the full test suite once (vitest run)
npm run build          # tsc -b (typecheck) && vite build
npm run preview        # preview the production build
```

Run a single test file: `npx vitest run src/db/entries.test.ts`
Run tests matching a name: `npx vitest run -t "upsertAttendance"`

There is no separate lint script; `npm run build` is the source of truth for type errors (TypeScript strict mode, `noUnusedLocals`/`noUnusedParameters` are on).

## Architecture

This is a **zero-backend, static single-page app** for teachers to track classroom progress, attendance, and student records. It is designed to run from any static host or directly via `file://` — there is no server and no account system. All data lives in the browser's IndexedDB; the only way data leaves or enters the browser is the explicit JSON backup export/import in `src/db/backup.ts`, plus the optional Google Sheets sync described below. This constraint drives several concrete choices below — don't casually introduce a server call or external API.

**Two deliberate exceptions**: the optional Google Sheets sync feature (`api/`, `src/db/sheetsSync.ts`) *does* need a small serverless backend, KV storage, and an online connection — see its own section below. It's additive and off by default (a teacher must click "구글 계정 연결하기" and complete Google's OAuth consent screen); every other feature in the app is unaffected and still works fully offline/`file://` with no account at all. The "시간표" feature (`api/timetable.ts`, `api/_lib/comci.ts`) is the second: it needs a server to proxy an external timetable site, but needs **no auth/session/KV at all** (it's public data) — see its own section below.

- `vite.config.ts` uses `base: './'` (relative asset paths, required for `file://`).
- `src/App.tsx` uses `HashRouter`, not `BrowserRouter` — routing must work without server-side rewrites.

### Data layer (`src/db/`)

Plain async functions wrapping a single Dexie (`AppDatabase`) instance in `src/db/db.ts` — no React imports in this directory. Each `*.ts` file owns one concern (`classes.ts`, `students.ts`, `curriculum.ts`, `progress.ts`, `entries.ts`, `backup.ts`, `seatingImport.ts`, `timetableSettings.ts`, plus `sheetsSync.ts` for the Sheets-sync feature — see its own section below) and is unit-tested in fake-indexeddb, not mocked — tests exercise real Dexie behavior.

Schema changes go through Dexie's versioning: add a new `this.version(N).stores({...})` block in `db.ts` (only the tables that changed), and an `.upgrade()` callback if existing data needs migrating (see version 2's migration of `classes.order`). Never edit an already-shipped `version()` block.

`src/db/entries.ts` unifies three physically separate tables — `attendance`, `stickers`, `records` (notes) — into one `Entry` union (`kind: 'attendance' | 'sticker' | 'note'`) via `listEntries`/`deleteEntry`/`updateAttendanceEntry`/`updateNoteEntry`. The `sticker` kind still exists in the data model and in `listEntries`/badge rendering, but no UI currently creates new sticker entries — it was removed from the record-entry forms as a deliberate simplification, not deleted from the schema.

`deleteClass` in `classes.ts` is the only cascading delete in the app: it removes a class's students, `classSubjects` links, progress, attendance, stickers, and records in one transaction. Any new per-class table needs to be added there too.

`ClassRecord` carries optional `seatRows`/`seatCols` (set via `classes.ts#updateSeatingSize`), read by `SeatingTab` with a `?? 6` fallback for classes that predate the feature — no Dexie migration was needed since these are unindexed fields. `updateSeatingSize` also unseats (sets `seatRow`/`seatCol` to `null`) any student who falls outside the new grid bounds, in the same transaction, so shrinking the grid can't leave orphaned coordinates. The rows/열 `<Input>`s in `SeatingTab` hold their own local draft state (`rowsInput`/`colsInput`), synced from the committed DB value via `useEffect` and only written back to the DB on blur/Enter — they used to be bound straight to the DB value with no buffer, so clearing the field mid-edit (e.g. backspace before retyping a two-digit number) produced an out-of-range/empty intermediate value that snapped straight back, making the field look frozen. Don't revert this to an onChange-commits-immediately pattern.

`students.ts#updateStudent`/`deleteStudent` are called from `RosterList.tsx` (설정 > 명단 관리) — the only place in the app with student edit/delete UI, see below.

**Subjects (과목)**: a teacher can teach more than one subject, and a class can have more than one subject taught to it (e.g. two back-to-back periods). `subjects` (`db/subjects.ts`) is a simple ordered list, and `classSubjects` (`db/classSubjects.ts`) is the many-to-many join table between `classes` and `subjects` — a class can be linked to any number of subjects (commonly 1, sometimes 2), toggled via badge buttons under each class row in `ClassManager.tsx` (설정 > 반 관리). `curriculum` items now belong to exactly one subject (`CurriculumItem.subjectId`, added in version 7) instead of being one single global list shared by every class — `curriculum.ts`'s `order` is scoped per-subject, not app-wide. `CurriculumManager.tsx` (설정 > 과목 관리 → 진도표 관리) requires picking a subject before showing/editing its items, the same class-scoped-`<Select>` pattern `RosterManager.tsx` uses for students. `ProgressTab.tsx` renders one progress card per subject linked to the class (via a `SubjectProgress` subcomponent so each card runs its own `useLiveQuery`s) — a class with zero linked subjects shows a guidance message instead of an empty/broken progress card. `deleteSubject` cascades: it removes the subject's `classSubjects` links, its `curriculum` items, and any `progress` rows referencing those items. The version-7 upgrade backfills existing installs by creating one default subject ("과목1") and pointing every pre-existing `curriculum` item and every pre-existing class at it, so nothing looks empty right after the upgrade. **Wired into Google Sheets sync**: `sheetsSync.ts`'s `TABLE_NAMES`/`SHEET_SCHEMA` (and the server-side duplicate in `api/_lib/tables.ts`) include `subjects`/`classSubjects` as two more tabs, and `curriculum`'s sheet columns include `subjectId`. Since this changes an already-deployed spreadsheet's shape (new tabs, and a new column inserted into the existing `curriculum` tab's header), `api/sheet.ts` calls `ensureSheetsExist()` on every GET/POST (not just on first connect / Picker-repoint) so an already-connected teacher's older sheet gets the missing tabs auto-created the next time they sync — cheap (one metadata call, no-op batchUpdate when nothing's missing). The `curriculum` tab's *header row*, though, only gets corrected by the next 내보내기 (export always rewrites the full tab including its header) — a 불러오기 (import) against a not-yet-re-exported older sheet will throw `SheetSchemaError` (header length/column mismatch) rather than silently misreading columns, which is the existing fail-loud behavior `gridToRecords` already had for any schema mismatch. Documented for the user in `docs/user-manual.md`'s Sheets section.

The original 7 tables (plus `subjects`/`classSubjects`, added in version 7) carry an `updatedAt?: string` (ISO, added in version 4) that is stamped automatically by `creating`/`updating` hooks registered on those tables in `db.ts` — **not** by the individual CRUD functions, which is why none of `classes.ts`/`students.ts`/`curriculum.ts`/`progress.ts`/`entries.ts`/`subjects.ts`/`classSubjects.ts` mention `updatedAt` at all. The hooks only fill it in when the caller didn't already supply one (`if (!record.updatedAt) ...`) — this is load-bearing: `sheetsSync.ts`'s `importFromSheet()` writes records with an explicit `updatedAt` taken from the sheet via `table.put()` (a full local-DB replace, not a merge — see the Google Sheets sync section), and that timestamp should reflect when the sheet row was actually last edited, not the moment it happened to be imported. `timetableSettings` (added in version 5, see the "시간표" section below) is a single-row device preference, not synced data, and isn't part of this hook loop.

### Routing / page structure (`src/App.tsx`, `src/pages/`)

Four top-level routes, each independently tabbed (except `/timetable`):
- `/` — `HomePage`, a class picker.
- `/setup/*` — `SettingsPage` owns its own tab bar (반 관리 / 과목 관리 / 진도표 관리 / 명단 관리 / 시간표 설정 / 백업 / Google 시트) over `src/pages/setup/*Page.tsx`, each a thin wrapper around a `*Manager` component.
- `/class/:classId/*` — `ClassPage` owns a 4-tab bar in this fixed order: **진도체크** (`ProgressTab`) → **출결확인** (`AttendanceTab`) → **누가기록** (`RecordsTab`) → **자리배치표** (`SeatingTab`). Tab order and Korean labels are meaningful UI decisions, not arbitrary — keep them in sync if reordering.
- `/timetable` — `TimetablePage`, a single page (no sub-tabs) showing the teacher timetable set up in 설정 > 시간표 설정, plus an on-page 학급 시간표 lookup section. See the "시간표" section below.

`src/components/layout/Shell.tsx`'s header title ("진도 췍") is a `<Link to="/">`, so it doubles as a home button; keep it a real link rather than a styled `<span>` if the header is touched again. `Shell.tsx` + `Sidebar.tsx` provide the persistent dark sidebar; the sidebar's class list order follows `classes.order` (drag-and-drop reorderable in `ClassManager`), not alphabetical. The sidebar is toggleable at every breakpoint via a ☰ button in `Shell`'s always-visible header (`Sidebar`'s `open`/`onClose` props, state owned by `Shell`): below `md` it's a fixed off-canvas drawer with a dimming backdrop (`Sidebar`'s conditional `md:hidden` backdrop `<div>`), at `md`+ it's `md:static` and toggling it just reflows the layout (`md:hidden` when closed) — no backdrop at that size since it's not blocking anything. Initial `sidebarOpen` state is decided once at mount via `window.matchMedia('(min-width: 768px)').matches` (open by default on tablet/desktop, closed on phones); `src/test/setup.ts` polyfills `window.matchMedia` since jsdom doesn't implement it. The sidebar's bottom section has a "📖 사용자 매뉴얼" button that opens `UserManualModal.tsx` (a summarized in-app guide); the full reference — including a table of every Google Sheets tab/column and which ones are safe to hand-edit — lives in `docs/user-manual.md`. Keep the two in sync if either changes.

### UI primitives (`src/components/ui/`)

A small hand-written shadcn/ui-*style* set (Button, Card, Input, Select, Label, Textarea, Table, Badge) styled with Tailwind v4. **`Select` and the checkboxes in this app are deliberately native `<select>`/`<input type="checkbox">`, not Radix primitives** — component tests drive them with `userEvent.selectOptions` / `getByRole('checkbox')`, which requires real form elements. Don't swap these for Radix Select/Checkbox without also reworking the tests that depend on native form semantics.

### Cross-cutting UI patterns

- Live data via `dexie-react-hooks`' `useLiveQuery` everywhere — never hold a manual copy of query results in `useState` and resync by hand; a past bug (see git history around `ProgressTab`) came from exactly that anti-pattern (an "optimistic update" local-state layer that drifted from the live-queried date). Read directly from `useLiveQuery`'s result.
- Native HTML5 drag-and-drop (`draggable` + `dataTransfer.setData/getData` in `onDragStart`/`onDrop`) is used for the seating chart (`SeatingTab`), class reordering (`ClassManager`), and curriculum reordering (`CurriculumManager`, via `reorderCurriculumItems` in `db/curriculum.ts`) — no drag-and-drop library. Pass the dragged id through `dataTransfer`, not through component state; component-state-tracked "currently dragging" ids raced against React's render timing.
- `QuickRecordForm` (student note entry) is rendered inside `NewRecordModal` (a lightweight fixed-overlay modal — see below), opened from `RecordsTab` via a "새 기록 추가" button or by clicking a student chip (which also sets `presetStudentId`). It used to be an always-visible inline form in `RecordsTab` and, before that, also lived in `ProgressTab`'s sidebar ("빠른 기록") — both were deliberately replaced/removed, so don't re-add an inline note-entry form to either tab.
- `NewRecordModal.tsx` and `UserManualModal.tsx` are the app's only modals, both the same hand-rolled pattern (no Dialog primitive, no Radix): a `fixed inset-0` backdrop `<div onClick={onClose}>` behind a centered card that calls `e.stopPropagation()` on click, `role="dialog" aria-modal="true"`, and the component returns `null` outright when `open` is false (so the wrapped form/content fully unmounts and resets on next open, rather than just being hidden). Follow this same shape for any new modal instead of reaching for a UI library.
- `RecentActivityList` is the shared read/edit/delete view over `listEntries`, used by both `AttendanceTab` (filtered to `kind: 'attendance'` + the selected `date`, as a toggleable history view) and `RecordsTab` (filtered to `kind: 'note'` + an optional `studentId`, as a toggleable history view). It accepts an optional `sortBy: 'date' | 'name'` prop — name-sort happens client-side in the component since `listEntries`/`EntryFilters` has no knowledge of student names. `RecordsTab` keeps two separate student-id states: `selectedStudentId` (presets the modal, also used to highlight the clicked chip) and `historyStudentId` (drives the history view's own "학생별 조회" select, defaulting to "전체 학생"/`undefined`) — they're intentionally decoupled so picking a student to add a record doesn't also filter the history view.
- Neither `AttendanceTab` nor `RecordsTab` has a student add/edit/delete UI — that lives in exactly one place, `RosterManager.tsx` (설정 > 명단 관리): a class-scoped `<Select>` (owned by `RosterManager`, lifted above its children) feeds a `classId` prop into both `RosterImport` (paste-to-bulk-add, disabled until a class is picked) and `RosterList` (inline number/name/role edit-on-blur, same pattern as `CurriculumManager`, plus a confirm-gated delete button — the row is two flex lines, not one, so the 이름 field doesn't get squeezed to near-zero width on narrow screens). `role` (e.g. 실장/부실장/도우미, free text, nullable) is optional per student and shown as a `Badge` next to the name in `AttendanceTab` when set. Keep per-tab pages (`AttendanceTab`, `RecordsTab`, `ProgressTab`) free of student add/edit/delete controls rather than duplicating this.
- `AttendanceTab`'s student list is a card-per-student `<ul>` (number+name on one line, the 4 status buttons on their own full-width line below), not a `<Table>` — the table layout used to squeeze 번호/이름 into a sliver of width on narrow screens while the status buttons wrapped onto two rows in a fixed-width column. `초기화` next to `전체 출석` clears every attendance mark for the selected date via `clearAttendanceForDate` in `entries.ts` (disabled when there's nothing to clear).

### Google Sheets sync (`api/`, `src/db/sheetsSync.ts`)

Optional, off by default. Lets a teacher explicitly push their data to (or pull it from) a Google Spreadsheet so it can be viewed/edited from either side. **Only this feature needs a server** — everything else stays IndexedDB-only. This is a **multi-tenant** design: one shared Vercel deployment serves many teachers, each connecting their own Google account to their own (separate, auto-created) spreadsheet — the server is a per-user relay, not a single shared credential. This is the one place in the app where a real login exists; every other feature works with no account.

Sync is **manual and one-directional per action, never automatic and never merged.** An earlier version auto-synced in the background (debounced on write + polled every 10s) with a pull→row-level-last-write-wins-merge→push cycle; it was replaced after this design proved unsafe across multiple devices — the merge join key was Dexie's local `++id` auto-increment, so two devices that independently created records could end up with colliding ids, and the merge would silently overwrite one device's unrelated record with the other's. There was also no concurrency control between the pull and the push, so a concurrent write from another device in that window got clobbered outright. Rather than harden that (client-generated globally-unique ids + server-side optimistic concurrency — both real options, but a materially bigger and riskier change, including a one-time id-remapping migration across all 7 tables' foreign keys and rewriting already-connected users' existing sheets), the feature was simplified to two explicit, user-triggered, full-overwrite actions instead — see below.

- `api/` (repo root, **not** `src/` — separate `api/tsconfig.json`, not part of `npm run build`'s `tsc -b`, typecheck it separately with `npx tsc -p api/tsconfig.json`) holds the Vercel Serverless Functions. `api/auth/google/start.ts` redirects to Google's consent screen (CSRF-protected via a random `state` value stored in a short-lived `oauth_state` cookie); `api/auth/google/callback.ts` verifies that state, exchanges the code for tokens (requesting `openid email` scope alongside `drive.file` so the token response includes an `id_token`), decodes the `sub`/`email` out of it, creates a spreadsheet titled `학급 진도 관리 동기화 (YYYY-MM-DD)` via `createSpreadsheet()` only when no KV record exists yet for that `sub` (an existing record reuses its `spreadsheetId` — this only happens on a plain re-login after session expiry, since disconnect deletes the record, see below), and issues a session cookie. `api/auth/me.ts` reports `{connected, email}` for the frontend's connection check; `api/auth/logout.ts` clears only the session; `api/auth/disconnect.ts` additionally revokes the Google token and deletes the user's KV record — see the logout-vs-disconnect distinction below. `api/sheet.ts` (GET pulls all of `TABLE_NAMES`' tabs, POST overwrites all of them — the only data endpoint the running app calls; it also calls `ensureSheetsExist()` on every request, see the subjects/과목 bullet in the Data layer section above for why) now authenticates via the session cookie instead of a shared token. `api/_lib/googleSheets.ts` is the plain-`fetch` Sheets API v4 wrapper; `api/_lib/oauth.ts` builds the authorize URL/redirect URI and decodes the `id_token` JWT payload (no signature re-verification needed — it's the value the server itself just got back from Google's token endpoint over TLS, not something that arrived from the client); `api/_lib/session.ts` wraps all cookie parsing/setting and KV access (session lookup, per-user Google-account record, AES-256-GCM encrypt/decrypt of the stored `refresh_token`); `api/_lib/tables.ts` holds the tab-name constants (9 as of the subjects feature; duplicated on purpose in `src/db/sheetsSync.ts` — `api/` and `src/` build separately and deliberately don't import from each other — keep both lists in sync when a table is added/removed).
- KV layout (Vercel KV via `@vercel/kv`): `session:{sessionId}` → `sub`, TTL 90 days, is the login session itself (opaque random ID in an httpOnly cookie — not a self-encoding signed token, so revoking a session is just deleting one KV key). `google-user:{sub}` → `{refreshToken (encrypted), spreadsheetId, email, createdAt}`, one per teacher, no TTL.
- **Logout vs. disconnect are deliberately different actions.** Logout (`api/auth/logout.ts`) only clears the session cookie/KV entry — the teacher's Google connection and spreadsheet stay intact for next time. Disconnect (`api/auth/disconnect.ts`) calls Google's revoke endpoint on the stored refresh_token and then deletes the whole `google-user:{sub}` KV record (`deleteUserRecord`) — reconnecting after a real disconnect always creates a **new** spreadsheet, it does not resume the old one. This was tried the other way once (keep `spreadsheetId`, drop only the token) and it doesn't work: revoking the OAuth grant with Google revokes `drive.file`'s per-file access too, not just the token, so a freshly-issued refresh_token from re-consenting gets `403 ACCESS_TOKEN_SCOPE_INSUFFICIENT` on the old file regardless of what `spreadsheetId` the server remembers — confirmed in production. The way to actually resume a specific old file after a real disconnect is Google Picker — see the dedicated bullet below. Don't collapse logout/disconnect into one action, and don't try the keep-spreadsheetId shortcut instead of Picker.
- **Privacy invariant, don't break it**: the server never persists student/class/attendance/record data — `api/sheet.ts` only relays it to/from Google Sheets per-request. The only thing KV stores about a teacher is their Google account identity and spreadsheet id, and the refresh_token is encrypted at rest with `KV_ENCRYPTION_KEY` specifically so that KV dashboard access alone doesn't hand over a usable credential.
- The server does zero merge logic — it's a dumb authenticated-per-user proxy, and there is no client-side merge logic either anymore. `src/db/sheetsSync.ts` exposes two independent, one-directional functions: `exportToSheet()` reads the full local state via `backup.ts`'s `exportData()`, converts it to grids with `recordsToGrid()`, and POSTs it — a full overwrite of the sheet. `importFromSheet()` GETs the sheet's grids, converts them with `gridToRecords()`, and hands the result to `backup.ts`'s `importData()` — the same clear-then-`bulkAdd` transaction the local JSON backup restore uses, so it's a full overwrite of local IndexedDB. Neither function takes a token/credential argument — `fetchSheet`/`pushSheet` (the shared internal helpers both call) send `credentials: 'include'` so the session cookie rides along automatically.
- Because each action is a full one-directional replace (never a row-by-row merge), there's no id-matching between devices and thus no `lastKnownIds`/deletion-heuristic bookkeeping to get wrong — deletions are just "the exported/imported side doesn't have that row anymore." This is a deliberate simplification, not an oversight: an earlier version auto-synced via a client-side pull→row-level-LWW-merge→push cycle keyed on Dexie's local `++id`, which could silently merge two devices' unrelated same-numbered records into one, plus had no concurrency control between its own pull and push. See the intro paragraph above for why that was replaced instead of hardened.
- **Google Picker** lets a connected teacher repoint sync at an existing spreadsheet instead of always using the one auto-created on first connect (most useful right after a real disconnect+reconnect, which otherwise starts a brand-new empty sheet). This is deliberately a separate, manual, always-available action — not wired into the OAuth `start.ts`/`callback.ts` redirect flow, which stays untouched and stays the low-friction path for a first-ever connect. Flow: `SheetsSyncManager.tsx`'s "다른 스프레드시트 선택" button calls `useSheetsSync.tsx`'s `selectSpreadsheet()`, which (1) GETs `api/auth/google/access-token.ts` — session-cookie-authenticated, mints a fresh short-lived `drive.file`-scoped access token from the stored refresh_token via the existing `getAccessToken()`, and is the *only* place a Google credential of any kind ever reaches the browser (client_secret and refresh_token never leave the server); (2) hands that token to `src/lib/googlePicker.ts`'s `pickSpreadsheet()`, which lazy-loads `https://apis.google.com/js/api.js` once and opens a Google-hosted Picker dialog restricted to Spreadsheets — this is the standard Google-documented pattern for combining narrow `drive.file` scope with letting a user browse/select any of their own existing files without broadening the OAuth scope; resolves with the picked file id, or `null` on cancel; (3) on a real pick, POSTs `api/auth/google/select-spreadsheet.ts` with `{ spreadsheetId }`, which mints its own fresh access token, calls `ensureSheetsExist()` (in `api/_lib/googleSheets.ts`) to create any of `TABLE_NAMES`' tabs the picked spreadsheet is missing — Picker can surface *any* of the user's spreadsheets, not just ones this app created, so this has to run before the sheet is usable — and only then overwrites the stored `spreadsheetId` in KV. `ensureSheetsExist()` is also called unconditionally at the top of `api/sheet.ts`'s handler (both GET and POST) as a second line of defense — this is what lets a teacher who connected before a table existed (e.g. `subjects`/`classSubjects`) get it auto-created on their next sync action, instead of only on a fresh connect or an explicit Picker repoint. Requires a new **public, referrer-restricted** Google API key (Picker needs a `developerKey` distinct from the OAuth `client_id`/`client_secret`) as the Vite build-time env var `VITE_GOOGLE_PICKER_API_KEY` — this one *is* meant to end up in the client bundle, unlike every other Google-related secret in this app; don't confuse it with `GOOGLE_CLIENT_SECRET`. Being a `VITE_`-prefixed var, it's baked in at build time, so adding/changing it requires a rebuild+redeploy to take effect, not just an env var change in the Vercel dashboard.
- `src/hooks/useSheetsSync.tsx` does **not** run anything automatically — no timers, no debounce, no polling, no dirty-write listener. `SheetsSyncProvider` is mounted once in `Shell.tsx` (not per-page) and exposes state via React Context (`useSheetsSync()`) to `Sidebar.tsx` (a static "연동됨" badge, no retry action) and `SheetsSyncManager.tsx` (connect/disconnect + the "내보내기"/"불러오기" buttons, each calling `exportNow()`/`importNow()` and each gated by a `window.confirm()` warning about the full-overwrite direction, matching `BackupManager.tsx`'s existing confirm pattern for the local JSON backup). `enabled` is set from an async `fetch('/api/auth/me')` on mount (fire-and-forget; a failed/errored fetch resolves to "not connected" rather than throwing).
- Local dev needs `vercel dev` (not plain `npm run dev`) to exercise `api/*`, which requires `vercel login` + `vercel link` once — not something this repo can do unattended, so `api/` changes are typically verified via the Vitest unit tests (`sheetsSync.test.ts` stubs `fetch`) rather than a live local server.
- **Deployed** at `https://jindocheckproject.vercel.app` (Vercel project `doo-lee/jindocheck_project`, linked via `vercel link` — `.vercel/` is gitignored). Source is also on GitHub (`github.com/mrdoolee/jindocheck_project`), but **`git push` does not auto-deploy** — the Vercel↔GitHub connection exists in Vercel's project config (`vercel git connect` reports "already connected") but no webhook actually fires on push (confirmed empty via `gh api repos/.../hooks` and by pushing a no-op commit and watching `vercel ls` — nothing new appeared); fixing it requires reconnecting through the Vercel *dashboard* UI (Project Settings → Git), which CLI-only linking doesn't fully replicate. Until that's done, **every push needs a manual `npx vercel deploy --prod --yes`** to actually go live — don't assume a push alone shipped anything, and don't report a fix as "deployed" without also running this. Required env vars: `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` (one shared OAuth client for the whole deployment), `KV_REST_API_URL`/`KV_REST_API_TOKEN` (auto-injected once a Vercel KV database is connected to the project — don't hand-enter these), `KV_ENCRYPTION_KEY` (32-byte hex, generate with `openssl rand -hex 32`, manual one-time setup), `VITE_GOOGLE_PICKER_API_KEY` (public Picker API key, HTTP-referrer-restricted to this app's domain(s) in Google Cloud Console, see the Picker bullet above). The old `VITE_SYNC_API_TOKEN` model is gone — the session itself still lives entirely in an httpOnly cookie, `VITE_GOOGLE_PICKER_API_KEY` is unrelated to auth and only exists for the Picker widget.
- When manually verifying a fresh deploy in a browser: **open a genuinely new tab**, not a hash-only re-navigation (`#/...`) on an already-loaded tab. This is a `HashRouter` SPA, so navigating to a different `#/route` on a page that's already loaded never re-fetches `index.html` or the JS bundle — you'll keep running whatever build was loaded when the tab first opened, silently testing stale code against a live redeploy. Confirm you're on the latest bundle by comparing the `<script src>` hash in the page to `curl -s https://jindocheckproject.vercel.app/ | grep -oP 'assets/index-\w+\.js'`.

### 시간표 (`api/timetable.ts`, `api/_lib/comci.ts`)

Optional, off by default (needs 설정 > 시간표 설정 filled in first). `TimetableSettings.mode` (`'comci' | 'manual'`, missing/undefined treated as `'comci'` for pre-existing rows) picks between two independent ways of populating the "시간표" page — a school that doesn't use comci.net can use manual entry instead of being locked out of the feature entirely. `TimetableSettingsManager.tsx` renders a `ModeToggle` plus either `ComciSettingsCard` (the flow described below, unchanged) or `ManualTimetableEditor`, and `TimetablePage.tsx` branches the same way (`ManualTimetableView` vs. the comci-fetching flow) — keep both branch points in sync if either is touched.

**Comci mode** shows a teacher's weekly timetable, scraped server-side from **컴시간알리미 (comci.net)** — an unofficial, undocumented, third-party school-timetable service, not an API this app controls or has a contract with. This needs **no auth/session/KV at all**: it's a stateless public-data proxy, `api/timetable.ts` never reads a cookie.

- comci.net doesn't support HTTPS, so a browser can't `fetch()`/iframe it directly from this app's HTTPS-served pages (mixed-content blocking, confirmed by testing) — `api/timetable.ts` fetches it server-side instead, where that restriction doesn't apply.
- `api/_lib/comci.ts#fetchSchoolData()` re-derives the request shape on every call rather than hardcoding it: it fetches comci's own `/st` HTML page (EUC-KR, decoded via `TextDecoder('euc-kr')` on a raw `arrayBuffer()` — the follow-up data endpoint is UTF-8, fine with plain `.text()`) and regex-extracts a dynamic endpoint number and a base64-query prefix from *that specific response*, live, every time — these looked stable when checked against a real school but are not something comci.net promises to keep constant.
- The response's field names (`자료147`, `자료492`, `자료446`, `자료481`, `자료542`, `분리`, `변경알림`, ...) are also comci-internal, not a documented contract. `findAssignedKey()` tries to *discover* three of them (`자료147`/`자료492`/`자료446`) from comci's own client JS via a Hangul-aware regex before falling back to the hardcoded names — a genuine improvement over the reference Apps Script this was ported from, whose equivalent regex used `[a-zA-Z0-9_]+` and could never match a Korean key name, so it silently always fell through to its hardcoded fallback. `분리` and `변경알림` are read from the response every time, never hardcoded — they're school-specific (a school with `분리≠1000` or `변경알림=0` decodes cells differently, see `getClassTimetable`/`getTeacherTimetable`).
- **If comci.net changes its response shape, this breaks** — that's the tradeoff of scraping an unofficial service. `fetchSchoolData()` throws a `ComciError` with a Korean message when the expected keys are missing rather than silently returning garbage; `api/timetable.ts` turns that into a 502 with the message intact.
- `getClassTimetable()` (given grade+반) and `getTeacherTimetable()` (given a teacher index) are pure functions over the parsed JSON — no network calls — specifically so they can be unit-tested against a hand-built fixture. `api/_lib/comci.test.ts` is **this repo's first `api/*.test.ts` file** (every other `api/` file is only typechecked, per the existing convention below) — worth the exception here because the cell-decoding logic (packed-integer encoding that swaps meaning depending on which array it came from, `>`-prefix vs baseline-diff change detection depending on `변경알림`) is intricate enough that a regression would be easy to miss without it.
- `src/db/timetableSettings.ts` (Dexie `timetableSettings` table, version 5) stores one row: `mode`, comci's schoolCode/teacherIndex/teacherName, and manual mode's `periodCount` (grid row count, default 7 when unset). It's a device preference, not classroom data — deliberately **not** synced through Google Sheets (`sheetsSync.ts`'s `TABLE_NAMES` doesn't include it), and `backup.ts#importData()` only clears/restores it when the payload actually included the key, so importing from Google Sheets (which never sets that key) doesn't wipe a device's timetable setting. Switching devices means re-picking the mode on each one — this was a deliberate scope call (see below), not an oversight.
- Local dev needs `vercel dev` for `api/timetable.ts` itself, same constraint as the Sheets endpoints — but unlike those, this feature has no session/OAuth setup required to test, just a valid comci.net school code. (Manual mode needs no `api/*` at all — it's pure IndexedDB, testable under plain `npm run dev`.)

**Manual mode**: `db/manualTimetable.ts` owns the `timetableEntries` table (Dexie version 8, `++id, [day+period]`) — one row per filled-in `(day 0–4=월–금, period 1-based)` cell, `{subject, note}`. `setManualTimetableCell()` upserts by the `[day+period]` compound index and **deletes** the row when both fields end up blank (so an emptied cell doesn't linger as a hollow record). Unlike `timetableSettings`, this is real content a teacher typed in — it's in the `updatedAt`-hook loop in `db.ts`, included in the local JSON backup (`backup.ts`, optional field for graceful old-backup import), and included in Google Sheets sync (`sheetsSync.ts`'s `TABLE_NAMES`/`SHEET_SCHEMA` and the server-side `api/_lib/tables.ts`) — the one thing about timetables that *is* synced, deliberately separate from the device-local `mode`/`periodCount`/comci fields. `ManualTimetableEditor` (settings page) and `ManualTimetableView` (the read-only "시간표" page, reusing `TimetableGridView` by mapping `{subject, note}` into the same `{subject, person, changed:false}` cell shape comci mode uses) both read/write this table directly — there's no "학급 시간표 조회" equivalent in manual mode, since that comci feature depends on comci's cross-class data which manual mode has no source for.

### Testing conventions

- `src/test/setup.ts` wires `fake-indexeddb/auto` (so Dexie code runs against a real, if in-memory, IndexedDB) plus `@testing-library/jest-dom`.
- Components using `useLiveQuery` resolve asynchronously even in tests — always `findBy*`/`waitFor` for the first assertion after render, never a synchronous `getBy*`, or the test will race the live query and become flaky/false-negative.
- `ProgressTab.test.tsx`'s "keeps progress independent between classes" test used to be occasionally flaky, including in isolation — the real cause: it `rerender()`s the same component with a different `classId` while both classes share the same subject, so the checkbox's DOM node persists across the rerender (same key) and `findByRole('checkbox')` resolves immediately with that still-checked node, racing the classId-scoped `progress` live-query's re-resolution instead of waiting for it. Fixed by wrapping that final assertion in `waitFor(...)` like the rest of the file's async assertions, instead of `findByRole` + a bare synchronous `expect`. If a similar test elsewhere reuses a component across a changed id/key prop, use the same `waitFor` pattern rather than trusting `findBy*` alone to wait for query re-resolution — it only waits for the element to exist, not for its live-query-driven content to catch up.
- `vite.config.ts`'s `test.exclude` deliberately excludes `.worktrees/` and `.claude/worktrees/` — without it, a stray git worktree under the repo root gets double-collected by Vitest and produces duplicate/failing test runs.
