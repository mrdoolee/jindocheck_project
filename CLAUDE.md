# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install          # install dependencies
npm run dev           # start Vite dev server
npm test              # run the full test suite once (vitest run)
npm run build          # tsc -b (typecheck) && vite build
npm run preview        # preview the production build
```

Run a single test file: `npx vitest run src/db/entries.test.ts`
Run tests matching a name: `npx vitest run -t "upsertAttendance"`

There is no separate lint script; `npm run build` is the source of truth for type errors (TypeScript strict mode, `noUnusedLocals`/`noUnusedParameters` are on).

## Architecture

This is a **zero-backend, static single-page app** for teachers to track classroom progress, attendance, and student records. It is designed to run from any static host or directly via `file://` — there is no server and no account system. All data lives in the browser's IndexedDB; the only way data leaves or enters the browser is the explicit JSON backup export/import in `src/db/backup.ts`, plus the optional Google Sheets sync described below. This constraint drives several concrete choices below — don't casually introduce a server call or external API.

**One deliberate exception**: the optional Google Sheets sync feature (`api/`, `src/db/sheetsSync.ts`) *does* need a small serverless backend, KV storage, and an online connection — see its own section below. It's additive and off by default (a teacher must click "구글 계정 연결하기" and complete Google's OAuth consent screen); every other feature in the app is unaffected and still works fully offline/`file://` with no account at all.

- `vite.config.ts` uses `base: './'` (relative asset paths, required for `file://`).
- `src/App.tsx` uses `HashRouter`, not `BrowserRouter` — routing must work without server-side rewrites.

### Data layer (`src/db/`)

Plain async functions wrapping a single Dexie (`AppDatabase`) instance in `src/db/db.ts` — no React imports in this directory. Each `*.ts` file owns one concern (`classes.ts`, `students.ts`, `curriculum.ts`, `progress.ts`, `entries.ts`, `backup.ts`, `seatingImport.ts`, plus `dirtyBus.ts`/`sheetsSync.ts` for the Sheets-sync feature — see its own section below) and is unit-tested in fake-indexeddb, not mocked — tests exercise real Dexie behavior.

Schema changes go through Dexie's versioning: add a new `this.version(N).stores({...})` block in `db.ts` (only the tables that changed), and an `.upgrade()` callback if existing data needs migrating (see version 2's migration of `classes.order`). Never edit an already-shipped `version()` block.

`src/db/entries.ts` unifies three physically separate tables — `attendance`, `stickers`, `records` (notes) — into one `Entry` union (`kind: 'attendance' | 'sticker' | 'note'`) via `listEntries`/`deleteEntry`/`updateAttendanceEntry`/`updateNoteEntry`. The `sticker` kind still exists in the data model and in `listEntries`/badge rendering, but no UI currently creates new sticker entries — it was removed from the record-entry forms as a deliberate simplification, not deleted from the schema.

`deleteClass` in `classes.ts` is the only cascading delete in the app: it removes a class's students, progress, attendance, stickers, and records in one transaction. Any new per-class table needs to be added there too.

`ClassRecord` carries optional `seatRows`/`seatCols` (set via `classes.ts#updateSeatingSize`), read by `SeatingTab` with a `?? 6` fallback for classes that predate the feature — no Dexie migration was needed since these are unindexed fields. `updateSeatingSize` also unseats (sets `seatRow`/`seatCol` to `null`) any student who falls outside the new grid bounds, in the same transaction, so shrinking the grid can't leave orphaned coordinates.

`students.ts#updateStudent`/`deleteStudent` are called from `RosterList.tsx` (설정 > 명단 관리) — the only place in the app with student edit/delete UI, see below.

All 7 tables carry an `updatedAt?: string` (ISO, added in version 4) that is stamped automatically by `creating`/`updating` hooks registered on every table in `db.ts` — **not** by the individual CRUD functions, which is why none of `classes.ts`/`students.ts`/`curriculum.ts`/`progress.ts`/`entries.ts` mention `updatedAt` at all. The hooks only fill it in when the caller didn't already supply one (`if (!record.updatedAt) ...`) — this is load-bearing: `sheetsSync.ts`'s pull-merge path writes records with an explicit `updatedAt` taken from the sheet via `table.put()`, and that timestamp must survive untouched for the next sync tick's last-write-wins comparison to be correct. If you ever "simplify" the hooks to always stamp `now()`, you will silently break sync conflict resolution.

### Routing / page structure (`src/App.tsx`, `src/pages/`)

Three top-level routes, each independently tabbed:
- `/` — `HomePage`, a class picker.
- `/setup/*` — `SettingsPage` owns its own tab bar (반 관리 / 진도표 관리 / 명단 관리 / 백업 / Google 시트) over `src/pages/setup/*Page.tsx`, each a thin wrapper around a `*Manager` component.
- `/class/:classId/*` — `ClassPage` owns a 4-tab bar in this fixed order: **진도체크** (`ProgressTab`) → **출결확인** (`AttendanceTab`) → **누가기록** (`RecordsTab`) → **자리배치표** (`SeatingTab`). Tab order and Korean labels are meaningful UI decisions, not arbitrary — keep them in sync if reordering.

`src/components/layout/Shell.tsx` + `Sidebar.tsx` provide the persistent dark sidebar; the sidebar's class list order follows `classes.order` (drag-and-drop reorderable in `ClassManager`), not alphabetical.

### UI primitives (`src/components/ui/`)

A small hand-written shadcn/ui-*style* set (Button, Card, Input, Select, Label, Textarea, Table, Badge) styled with Tailwind v4. **`Select` and the checkboxes in this app are deliberately native `<select>`/`<input type="checkbox">`, not Radix primitives** — component tests drive them with `userEvent.selectOptions` / `getByRole('checkbox')`, which requires real form elements. Don't swap these for Radix Select/Checkbox without also reworking the tests that depend on native form semantics.

### Cross-cutting UI patterns

- Live data via `dexie-react-hooks`' `useLiveQuery` everywhere — never hold a manual copy of query results in `useState` and resync by hand; a past bug (see git history around `ProgressTab`) came from exactly that anti-pattern (an "optimistic update" local-state layer that drifted from the live-queried date). Read directly from `useLiveQuery`'s result.
- Native HTML5 drag-and-drop (`draggable` + `dataTransfer.setData/getData` in `onDragStart`/`onDrop`) is used for both the seating chart (`SeatingTab`) and class reordering (`ClassManager`) — no drag-and-drop library. Pass the dragged id through `dataTransfer`, not through component state; component-state-tracked "currently dragging" ids raced against React's render timing.
- `QuickRecordForm` (student note entry) is used by `RecordsTab`'s add-form view; it accepts an optional `presetStudentId` so clicking a student in the sidebar list pre-fills it. It used to also live in `ProgressTab`'s sidebar ("빠른 기록") — that was deliberately removed, so don't re-add a note-entry shortcut to `ProgressTab`.
- `RecentActivityList` is the shared read/edit/delete view over `listEntries`, used by both `AttendanceTab` (filtered to `kind: 'attendance'` + the selected `date`, as a toggleable history view) and `RecordsTab` (filtered to `kind: 'note'` + an optional `studentId`, as a toggleable history view). It accepts an optional `sortBy: 'date' | 'name'` prop — name-sort happens client-side in the component since `listEntries`/`EntryFilters` has no knowledge of student names. `RecordsTab` keeps two separate student-id states: `selectedStudentId` (presets the add-form, cleared by "전체 학생 보기") and `historyStudentId` (drives the history view's own "학생별 조회" select, defaulting to "전체 학생"/`undefined`) — they're intentionally decoupled so picking a student to add a record doesn't also filter the history view.
- Neither `AttendanceTab` nor `RecordsTab` has a student add/edit/delete UI — that lives in exactly one place, `RosterManager.tsx` (설정 > 명단 관리): a class-scoped `<Select>` (owned by `RosterManager`, lifted above its children) feeds a `classId` prop into both `RosterImport` (paste-to-bulk-add, disabled until a class is picked) and `RosterList` (inline number/name edit-on-blur, same pattern as `CurriculumManager`, plus a confirm-gated delete button). Keep per-tab pages (`AttendanceTab`, `RecordsTab`, `ProgressTab`) free of student add/edit/delete controls rather than duplicating this.

### Google Sheets sync (`api/`, `src/db/sheetsSync.ts`)

Optional, off by default. Lets the app's data live-sync with a Google Spreadsheet so it can be viewed/edited from either side. **Only this feature needs a server** — everything else stays IndexedDB-only. This is a **multi-tenant** design: one shared Vercel deployment serves many teachers, each connecting their own Google account to their own (separate, auto-created) spreadsheet — the server is a per-user relay, not a single shared credential. This is the one place in the app where a real login exists; every other feature works with no account.

- `api/` (repo root, **not** `src/` — separate `api/tsconfig.json`, not part of `npm run build`'s `tsc -b`, typecheck it separately with `npx tsc -p api/tsconfig.json`) holds the Vercel Serverless Functions. `api/auth/google/start.ts` redirects to Google's consent screen (CSRF-protected via a random `state` value stored in a short-lived `oauth_state` cookie); `api/auth/google/callback.ts` verifies that state, exchanges the code for tokens (requesting `openid email` scope alongside `drive.file` so the token response includes an `id_token`), decodes the `sub`/`email` out of it, creates a spreadsheet via `createSpreadsheet()` only on a user's *first* connection (a returning `sub` reuses its existing `spreadsheetId`), and issues a session cookie. `api/auth/me.ts` reports `{connected, email}` for the frontend's connection check; `api/auth/logout.ts` clears only the session; `api/auth/disconnect.ts` additionally revokes the Google token and deletes the user's KV record — see the logout-vs-disconnect distinction below. `api/sheet.ts` (GET pulls all 7 tabs, POST overwrites all 7 tabs — the only data endpoint the running app calls) now authenticates via the session cookie instead of a shared token. `api/_lib/googleSheets.ts` is the plain-`fetch` Sheets API v4 wrapper; `api/_lib/oauth.ts` builds the authorize URL/redirect URI and decodes the `id_token` JWT payload (no signature re-verification needed — it's the value the server itself just got back from Google's token endpoint over TLS, not something that arrived from the client); `api/_lib/session.ts` wraps all cookie parsing/setting and KV access (session lookup, per-user Google-account record, AES-256-GCM encrypt/decrypt of the stored `refresh_token`); `api/_lib/tables.ts` holds the 7 tab-name constants (duplicated on purpose in `src/db/sheetsSync.ts` — `api/` and `src/` build separately and deliberately don't import from each other).
- KV layout (Vercel KV via `@vercel/kv`): `session:{sessionId}` → `sub`, TTL 90 days, is the login session itself (opaque random ID in an httpOnly cookie — not a self-encoding signed token, so revoking a session is just deleting one KV key). `google-user:{sub}` → `{refreshToken (encrypted), spreadsheetId, email, createdAt}`, one per teacher, no TTL.
- **Logout vs. disconnect are deliberately different actions.** Logout (`api/auth/logout.ts`) only clears the session cookie/KV entry — the teacher's Google connection and spreadsheet stay intact for next time. Disconnect (`api/auth/disconnect.ts`) calls Google's revoke endpoint on the stored refresh_token and clears it from the `google-user:{sub}` KV record via `clearUserToken()` — but **keeps** `spreadsheetId`/`email`/`createdAt`. This is deliberate, not a partial implementation: with `drive.file` scope the server has no way to look up a teacher's spreadsheet again once the mapping is gone (no Drive-listing permission), so deleting the whole record on disconnect meant reconnecting the same Google account silently created a second, orphaned spreadsheet instead of resuming the original — a real bug hit in production. `api/auth/google/callback.ts`'s reuse check (`existing ? existing.spreadsheetId : createSpreadsheet(...)`) only looks at whether a record exists, not whether its token is valid, so this fix required no callback changes. Don't collapse logout/disconnect into one action, and don't "simplify" disconnect back to a full record delete without re-solving the reconnect problem (Google Picker is the alternative, deliberately not chosen here — see git history / session log for the tradeoff).
- **Privacy invariant, don't break it**: the server never persists student/class/attendance/record data — `api/sheet.ts` only relays it to/from Google Sheets per-request. The only thing KV stores about a teacher is their Google account identity and spreadsheet id, and the refresh_token is encrypted at rest with `KV_ENCRYPTION_KEY` specifically so that KV dashboard access alone doesn't hand over a usable credential.
- The server does zero merge logic — it's a dumb authenticated-per-user proxy. All conflict/merge decisions happen client-side in `src/db/sheetsSync.ts`'s `syncTick()`, because that's the only place that actually holds the Dexie state. `syncTick()` takes no token/credential argument anymore — `fetchSheet`/`pushSheet` send `credentials: 'include'` so the session cookie rides along automatically.
- `syncTick()` is always **pull → merge → push**, never two independent timers — pushing without pulling first would blindly overwrite whatever changed sheet-side since the last pull. Merge is last-write-wins by `updatedAt`. Deletion is symmetric without soft-delete: each browser keeps a `lastKnownSheetIds` map in `localStorage`, and only treats "in `lastKnownIds` but missing from this pull, still present locally" as a real deletion (as opposed to "not yet pushed") — see `mergeTable()`. Deletes go through the existing `deleteClass`/`deleteStudent`/`deleteCurriculumItem`/`deleteEntry` functions (not raw `table.delete()`), so cascade rules still apply. **`lastKnownIds` is computed from the post-merge local state right before the push (`payload.data[name]` in `syncTick()`), not from the pull.** This was a real bug once: computing it from the pre-push pull meant a row pushed for the first time in tick N looked "never seen" on tick N+1, so deleting it locally between ticks got it silently resurrected from the sheet before the sheet had caught up. If you touch this ordering, re-run `sheetsSync.test.ts`'s two-tick regression test (`does not resurrect a row deleted right after the tick that first pushed it`) — a single-tick test isn't enough to catch this class of bug.
- `src/hooks/useSheetsSync.tsx` runs sync automatically, app-wide: `SheetsSyncProvider` is mounted once in `Shell.tsx` (not per-page) and exposes state via React Context (`useSheetsSync()`) to `Sidebar.tsx` (status badge), `SheetsSyncManager.tsx` (connect/disconnect + manual "지금 동기화" button). **Don't** call `useSheetsSync()` from more than one place per render tree, or you'll get two independent timers/pollers double-syncing. `enabled` is no longer a build-time env check — it's set from an async `fetch('/api/auth/me')` on mount (fire-and-forget; a failed/errored fetch resolves to "not connected" rather than throwing, so a network hiccup during that check doesn't crash the provider). Automatic triggers — debounced (4s after a local Dexie write) and polled (every 10s) — are gated on `document.visibilityState === 'visible'` so a backgrounded tab does nothing; the manual "지금 동기화" button (`syncNow`) deliberately does **not** check visibility, since a user who clicked it is obviously looking at the tab right now — a Page Visibility API quirk under automated/CDP-driven browsers (visibility can read `'hidden'` even when nothing is actually backgrounded) makes this distinction easy to get backwards, so don't add a visibility check back into `runTick`/`syncNow` itself.
- `src/db/dirtyBus.ts` is how "a local write happened" reaches the hook without polling Dexie itself: `db.ts`'s `creating`/`updating`/`deleting` hooks call `notifyDirty()` on every write. `sheetsSync.ts`'s own pull-merge step writes to Dexie too (via `table.put()`/the delete functions) — that would otherwise immediately re-trigger the debounced listener after every tick, so `syncTick()` wraps its merge loop in `withDirtySuppressed()` to swallow those specific notifications. Only the merge loop is wrapped; the push step's `exportData()` call is a read, so it's fine outside the suppression.
- Local dev needs `vercel dev` (not plain `npm run dev`) to exercise `api/*`, which requires `vercel login` + `vercel link` once — not something this repo can do unattended, so `api/` changes are typically verified via the Vitest unit tests (`sheetsSync.test.ts` stubs `fetch`) rather than a live local server.
- **Deployed** at `https://jindocheckproject.vercel.app` (Vercel project `doo-lee/jindocheck_project`, linked via `vercel link` — `.vercel/` is gitignored). `npx vercel deploy --prod --yes` ships a new production deployment. Required env vars: `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` (one shared OAuth client for the whole deployment), `KV_REST_API_URL`/`KV_REST_API_TOKEN` (auto-injected once a Vercel KV database is connected to the project — don't hand-enter these), `KV_ENCRYPTION_KEY` (32-byte hex, generate with `openssl rand -hex 32`, manual one-time setup). No frontend/build-time env var is needed anymore — the old `VITE_SYNC_API_TOKEN` model is gone; the session lives entirely in an httpOnly cookie.
- When manually verifying a fresh deploy in a browser: **open a genuinely new tab**, not a hash-only re-navigation (`#/...`) on an already-loaded tab. This is a `HashRouter` SPA, so navigating to a different `#/route` on a page that's already loaded never re-fetches `index.html` or the JS bundle — you'll keep running whatever build was loaded when the tab first opened, silently testing stale code against a live redeploy. Confirm you're on the latest bundle by comparing the `<script src>` hash in the page to `curl -s https://jindocheckproject.vercel.app/ | grep -oP 'assets/index-\w+\.js'`.

### Testing conventions

- `src/test/setup.ts` wires `fake-indexeddb/auto` (so Dexie code runs against a real, if in-memory, IndexedDB) plus `@testing-library/jest-dom`.
- Components using `useLiveQuery` resolve asynchronously even in tests — always `findBy*`/`waitFor` for the first assertion after render, never a synchronous `getBy*`, or the test will race the live query and become flaky/false-negative.
- `ProgressTab.test.tsx`'s "keeps progress independent between classes" test is known to be occasionally flaky **only** when the full suite runs in parallel (a `useLiveQuery` re-resolution timing sensitivity under CPU contention); it passes reliably in isolation. Don't chase this one in isolation — verify with `npx vitest run src/pages/class/ProgressTab.test.tsx` before treating a full-suite failure there as a real regression.
- `vite.config.ts`'s `test.exclude` deliberately excludes `.worktrees/` and `.claude/worktrees/` — without it, a stray git worktree under the repo root gets double-collected by Vitest and produces duplicate/failing test runs.
